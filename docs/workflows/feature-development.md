# 기능 개발

작업의 규모에 맞춰 절차를 조정합니다. 작은 수정도 어떤 동작을 바꾸고 어떻게 확인할지 정한 뒤
시작합니다.

## 작업 순서

1. 요청이나 GitHub 이슈에서 목표, 범위, 완료 기준을 확인합니다. 디자인이 제공되면 함께 읽고,
   구현·계획·리뷰 중 요청한 산출물을 확인합니다.
2. `git status --short --branch`로 현재 브랜치와 변경사항을 확인합니다. 이전 작업에서 이어지는
   경우 최근 커밋도 살핍니다.
3. 대상 화면의 라우트와 레이아웃에서 기능 컴포넌트, 훅, API로 이어지는 흐름을 확인합니다.
   시작점이 불명확하면 [저장소 구조](../architecture/repo-structure.md)를 참고합니다.
   비슷한 동작을 가진 기존 구현과 관련 문서를 읽습니다.
4. 코드의 소유 위치를 정합니다. 라우트, 기능 전용 코드, 공용 UI의 기준은
   [앱 구조](../architecture/app-structure.md)를 따릅니다. 에이전트는 `AGENTS.md`의 표에서
   변경할 경계에 맞는 스킬을 선택합니다.
5. 요청 범위 안에서 구현합니다. 공용 UI나 API는 호출하는 화면을 확인하고, 다른 화면이 같은
   데이터를 쓰면 변경 후 조회 결과도 확인합니다. 보호 경로는 인증 전후의 진입과 복귀를 확인합니다.
6. [검증](verification.md)에서 변경에 맞는 정적 검사와 사용자 흐름을 확인합니다.
7. 구현한 내용과 검증 결과를 정리합니다. PR은 [Git과 GitHub](../conventions/git.md)의 작성 기준을
   따릅니다.

여러 화면이나 API가 걸친 작업은 구현 전에 사용자 동작, 변경할 경계, 기존 사용처에 미치는 영향과
검증 방법을 짧게 정리합니다. 예를 들어 결제 등록 화면과 요청이 함께 바뀌면 페이지와 폼의 소유
위치를 정한 뒤 API 계약과 캐시 갱신을 확인합니다.

문서·설정 변경은 해당 기준 문서와 기존 파일에서 시작합니다. 실행 환경이나 스크립트가 바뀌면
[로컬 개발](local-development.md) 문서와 `package.json`을 대조합니다.

자료에서 확인할 수 없는 요구사항이 사용자 동작이나 API 계약에 영향을 주면 구현 전에 필요한 사항을
확인합니다.

## 완료 기준

- 요청한 동작을 직접 확인했습니다. 화면 변경은 관련 실패와 빈 상태, 모바일 레이아웃도 살핍니다.
- 구조나 규칙이 바뀌었다면 해당 기준 문서에 반영했습니다.
- 실행한 검사와 확인하지 못한 동작을 기록했습니다.

# 앱 구조와 의존성

Belog는 Next.js App Router에서 URL과 레이아웃을 관리합니다. 기능별 화면과 상태는 `src/features`에
모으고, 여러 기능에서 공통으로 쓰는 UI와 외부 연동에 각각의 위치를 둡니다.

## 기본 구조

```text
src/
  app/
    (auth)/
    (main)/
    api/
    invitations/
    oauth/
    layout.tsx
    providers.tsx
    globals.css
  features/
  components/
    ui/
    layout/
  hooks/
  lib/
  constants/
  types/
```

## 디렉터리 역할

| 위치 | 관리하는 코드 |
| --- | --- |
| `app` | URL, 레이아웃, 메타데이터, 전역 프로바이더, Route Handler |
| `features` | 인증, 홈, 그룹, 만남, 세 로그, 마이, 알림, 온보딩, PWA의 기능 모듈 |
| `components/ui` | 버튼, 입력 필드, 모달, 탭처럼 여러 화면에서 사용하는 UI |
| `components/layout` | 헤더, 하단 내비게이션, 캘린더처럼 화면을 구성하는 공통 요소 |
| `hooks` | 토스트나 디바운스처럼 기능 간에 공유하는 훅 |
| `lib` | Axios·Firebase·Amplitude 연동과 날짜·이미지 처리 유틸 |
| `constants` | API 엔드포인트와 Google OAuth 설정 등 앱 전역 상수 |
| `types` | Kakao Maps처럼 브라우저에서 사용하는 외부 API의 타입 선언 |

## 라우팅과 보호 경로

- `(auth)`는 랜딩·로그인·가입 화면을 묶고, `(main)`은 인증이 필요한 화면을 묶습니다. 괄호로 표시한
  라우트 그룹은 URL에서 생략됩니다.
- `(main)` 레이아웃은 브라우저에서 인증을 확인해 화면 진입을 제어하고, 인증된 화면에 푸시 알림과 PWA
  설치 이벤트를 연결합니다. 하단 탭은 홈, 그룹, 마이 화면에서 표시합니다.
- 메모리에 액세스 토큰이 없으면 갱신 쿠키로 토큰 재발급을 시도합니다. 재발급에 실패하면 랜딩으로
  이동하고, 재발급 응답에 온보딩이 필요하다고 표시되면 프로필 등록으로 이동합니다.
- OAuth 콜백과 초대 링크는 인증 전에도 열 수 있는 진입점입니다. 초대 링크는 코드를 저장하고 그룹
  참여 화면으로 보내며, 로그인이 필요하면 인증을 거친 뒤 참여 흐름으로 돌아옵니다.
- 페이지는 경로 파라미터를 처리하고 해당 화면을 조합합니다. 그룹과 만남 상세 페이지는 ID를 양의
  정수로 검증하고, 잘못된 값은 `notFound()`로 처리합니다. 서버에서 URL을 검증하고 기능 컴포넌트에
  ID를 전달하는 예입니다.
- `app/api`는 서버에서 처리하는 HTTP 경계입니다. 권한 확인이 필요한 HTTP 요청은 해당 Route Handler나
  백엔드 API에서 처리합니다. Post-log 티켓의 커버 이미지를 가져오는 이미지 프록시도 이 경계에
  있습니다.

## 주요 화면

| 화면 | URL | 관련 기능 |
| --- | --- | --- |
| 홈 | `/` | 홈 페이지가 `home`의 캘린더, 만남 목록, 시작 안내를 조합합니다. |
| 그룹 | `/group`, `/group/[id]` | `group`이 목록, 그룹 상세와 참여를 관리합니다. |
| 만남 상세 | `/meetup/[id]` | `meetup`이 만남 정보, 참여자와 날짜 투표를 관리합니다. |
| 모임 기록과 정산 | `/pre-log`, `/post-log`, `/bill-log` | 각 로그가 `meetingId`로 만남을 찾아 화면을 구성합니다. |
| 개인 화면 | `/my`, `/notification` | 프로필·추억 캘린더와 알림 목록을 제공합니다. |
| 설정 | `/setting`, `/setting/account` | 설정 페이지는 인증·알림·PWA 기능을 조합하고 계좌 관리는 `my`의 훅을 사용합니다. |
| 로그인과 가입 | `/landing`, `/login`, `/register/profile` | `auth`가 로그인 진입과 가입 흐름을 관리합니다. |
| 콜백과 초대 | `/oauth/google/callback`, `/invitations/[code]` | 로그인 결과와 초대 링크에서 앱으로 돌아옵니다. |

## 기능과 공통화

### 기능 내부 구성

기능 코드는 `src/features/{feature}`에 둡니다. 예를 들어 그룹 목록은 `GroupList`가 표시하고,
`useGroups`가 조회 상태를 관리하며, `groupApi`가 백엔드 요청을 보냅니다.

- 한 기능에서 사용하는 컴포넌트, 훅, API와 타입은 해당 기능에 둡니다. 상태 저장소나 유틸, 상수가
  필요한 경우에 해당 하위 폴더를 사용합니다.
- 요청과 화면 조합이 복잡한 경우 그룹 상세의 Container/View 패턴을 참고합니다. 컨테이너는 조회와
  변경 요청을 연결하고, 뷰는 받은 데이터와 동작을 표시하며 탭이나 모달 같은 화면 상태를 관리합니다.
- 새 화면의 조회나 변경 로직은 기능 컴포넌트와 훅에 두는 것을 기본으로 합니다. 결제 등록처럼 기존
  페이지가 화면 단계와 이동을 맡는 흐름을 수정할 때는 해당 책임과 호출 관계를 먼저 확인합니다.

### 공용 코드로 옮기는 기준

- 여러 화면에서 사용하면서 역할과 변경 이유가 같은 UI는 `components/ui` 또는 `components/layout`에
  둡니다. 제품 동작이 들어간 코드는 해당 기능이 소유합니다.
- 공용 UI의 props나 동작을 바꿀 때는 기존 사용 화면과 영향 범위를 먼저 확인합니다. 다른 작업에
  영향을 주는 계약 변경은 팀에 공유합니다.
- 기능 간에 같은 API 응답이나 타입을 사용하면 소유 기능의 훅과 타입을 재사용합니다. 예를 들어
  Bill-log 결제 등록의 참여자 선택에는 만남 기능의 참여자 조회 훅을 사용합니다.

## 서버와 클라이언트 경계

- 페이지와 레이아웃은 서버 컴포넌트를 기본으로 둡니다. 상태, 이벤트 핸들러, 브라우저 API를 사용하는
  컴포넌트 경계에 `"use client"`를 둡니다.
- 공통 QueryClient와 Amplitude 초기화는 클라이언트 프로바이더가 담당합니다. `(main)` 레이아웃도
  브라우저에서 인증 상태와 PWA 이벤트를 처리하는 클라이언트 경계입니다.
- 클라이언트에서 `useSearchParams`를 사용하면 호출부의 `Suspense` 경계를 함께 확인합니다. Post-log는
  페이지에서 내부 화면을 `Suspense`로 감쌉니다.

## API와 상태

### 요청과 인증

- 브라우저에서 백엔드를 호출하는 함수는 기능의 `api`에 두고 공통 Axios 인스턴스, `ENDPOINTS`,
  `ApiResponse`와 `ApiError`를 사용합니다. `ENDPOINTS`는 백엔드 API용이고, 화면 이동은 App Router의
  URL을 사용합니다.
- 공통 Axios는 메모리 토큰, 공유 갱신 상태와 브라우저 이동에 의존합니다. Server Component나 Route
  Handler에서 백엔드를 호출할 때는 인증 정보와 상태를 해당 서버 요청 범위에서 처리합니다.
- Google OAuth 콜백은 인가 코드를 백엔드 로그인 API에 전달합니다. 요청 인터셉터는 메모리의 액세스
  토큰을 사용합니다. 토큰 갱신은 쿠키를 사용하고 동시에 실행된 갱신 요청은 하나로 합칩니다.
- 재시도 대상인 API가 401을 반환하면 토큰 갱신 후 원래 요청을 한 번 다시 보냅니다. 갱신 실패 시
  토큰을 비우고 로그인으로 이동합니다. 이 흐름을 변경할 때는 초기 인증 가드, 온보딩과 초대 복귀도
  함께 확인합니다.
- Presigned URL의 파일 전송은 스토리지에 직접 `fetch`하고 기능의 업로드 계약에 맞는 헤더를
  사용합니다. 그룹 커버는 파일의 `Content-Type`을, Post-log 사진은 발급 응답의 `requiredHeaders`를
  보냅니다. Post-log는 업로드 후 백엔드에 사진 메타데이터를 등록합니다.

### 조회와 화면 상태

- 서버 상태는 TanStack Query로 관리합니다. 키 팩토리가 있는 기능은 이를 사용합니다. `setQueryData`로
  캐시를 직접 갱신할 때는 식별자와 필터가 포함된 전체 조회 키를 사용합니다. 여러 조회를 함께
  무효화할 때는 대상 범위를 확인한 뒤 접두 키를 사용합니다. 예를 들어
  `preLogKeys.allPlans(meetingId)`는 해당 만남의 필터별 계획 목록을 모두 무효화할 때 사용합니다.
- 만남 수정처럼 같은 정보를 여러 화면에서 읽는 경우 관련 캐시를 함께 무효화합니다. 현재 만남 수정은
  만남 상세, 그룹, 홈, 해당 만남의 Pre-log 메인 조회를 무효화합니다.
- 낙관적 갱신은 그룹 핀의 흐름을 참고합니다. 진행 중인 조회를 취소하고 이전 값을 보관한 뒤, 실패 시
  복구하고 완료 후 다시 조회합니다.
- 탭, 모달과 같이 한 화면에만 필요한 UI 상태는 React를 사용합니다. 결제 등록의 여러 단계나 PWA 설치
  이벤트처럼 여러 컴포넌트에 걸쳐 공유하는 클라이언트 상태에는 Zustand를 사용합니다.

## 로딩과 오류 처리

- 화면에 필요한 조회는 해당 컨테이너나 화면에서 로딩, 오류와 빈 결과를 표현합니다. 그룹 상세는 최초
  조회가 실패하면 오류와 다시 시도 버튼을 표시합니다. 지난 만남은 별도 요청으로 처리해 전체 화면
  표시와 분리합니다.
- 로딩이나 실패를 빈 결과로 표현하면 사용자가 데이터가 실제로 없는 것으로 받아들일 수 있습니다. 새
  조회를 연결할 때는 로딩, 요청 실패, 정상 응답의 빈 데이터를 구분합니다.
- 입력이나 요청이 실패할 수 있는 저장 흐름은 진행 상태와 실패 후 할 수 있는 동작을 함께 보여 줍니다.

## PWA와 웹 푸시

- next-pwa는 프로덕션 빌드에서 `public`에 캐싱용 서비스 워커를 생성합니다. Firebase Messaging은 별도
  scope의 `public/firebase-messaging-sw.js`를 사용합니다.
- 알림의 클릭 목적지가 바뀌면 앱의 `getNotificationPath`와 FCM 워커의 매핑을 함께 확인합니다.

## 의존 방향

`app`이 기능과 공용 UI를 조합하고, 기능은 공용 UI·훅과 외부 연동을 사용합니다. 앱 내부에서 새 공용
코드를 추가할 때는 특정 기능을 import하지 않고 필요한 화면 데이터와 동작을 props로 받도록
구성합니다.

```text
app → features, components, hooks, lib, constants
features → components, hooks, lib, constants
components, hooks → lib, constants
```

기능 간 연결이 필요한 경우 호출하는 쪽과 데이터를 소유하는 쪽을 확인하고 순환 의존을 피합니다. 현재
공용 `Header`는 알림 기능의 읽지 않은 알림 훅을 직접 사용합니다. 헤더를 수정할 때는 이 연결과 사용
화면을 함께 확인합니다.

# 기능 구현

## 먼저 읽을 기준

- `docs/architecture/app-structure.md`의 기능과 공통화
- `docs/conventions/conventions.md`

대상 기능에서 가까운 기존 구현을 함께 읽습니다.

## 작업 순서

1. 화면, 훅, 상태, 타입의 소유 기능을 정합니다. 기존 하위 폴더에서 변경과 직접 관련된 위치를
   사용합니다.
2. 데이터 요청과 화면 조합이 복잡하면 그룹 상세의 Container/View 구성을 참고합니다. 화면 로컬 상태와
   여러 단계에서 공유할 상태를 구분합니다.
3. 기존 기능에서 제공하는 훅이나 타입을 재사용합니다. 같은 서버 데이터를 여러 화면에서 표시하면
   조회와 갱신 범위를 확인합니다.
4. 쿼리나 API 변경이 있으면 `api-integration-workflow`의 계약과 캐시 검토를 적용합니다.

## 코드 배치와 공통화

기능에 종속된 컴포넌트, 유틸과 상태는 소유 기능에 둡니다. 공용화는 다른 사용처가 실제로 같은 동작과
계약을 필요로 할 때 검토합니다. 여러 단계에서 사용하는 결제 폼처럼 공유 범위가 분명하면 해당 기능의
Zustand 패턴을 참고합니다.

## 완료

초기값, 화면 상태, 기능 간에 전달하는 값과 주요 사용자 흐름을 확인합니다.
